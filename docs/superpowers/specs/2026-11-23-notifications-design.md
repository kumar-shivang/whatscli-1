# Notifications: design

_Last updated: 2026-11-23T08:47:24+00:00 (default on). Branch: `feature/notifications`._

## Why

Notifications already exist but are too basic for daily use. They are off by default, a busy group sends one pop-up per message, group pop-ups don't say which group, muted chats still notify, media messages give an empty or odd body, and nothing happens for the chat you have open even when you're in another window. The goal is notifications good enough to leave on all day, with a sound, so whatscli can replace WhatsApp Web as the place you get messages.

## What exists today

- `messages/session_manager.go:241` `notify(title, message)`: does nothing unless `general.enable_notifications`; with `general.use_terminal_bell` it prints `\a`; otherwise it calls `beeep.Notify`.
- `messages/event_handler.go:296` calls it for an incoming message (not from me) in a chat that is **not** open, if the message is under 30 s old. Title is the sender label, body is `text`.
- `general.notification_timeout` (default 60) is documented as "seconds between repeated notifications" but nothing reads it.
- No mute state anywhere. `conversations` has `is_pinned`, `is_archived`.
- `extractMessageContent` (`messages/event_handler.go:70`) already returns a `preview` (e.g. a label for photos) used by the chat list.

## Goals

1. **Who and where:** the pop-up title names the sender, plus the group for group chats: `Asha · Family`. For a direct chat, the title is just the contact name.
2. **Readable body:** use `text`; if it's empty (media), use `preview`. Cut it to about 100 characters.
3. **Throttle:** at most one notification (pop-up and sound) per chat within each `notification_timeout` seconds. 0 means no throttle.
4. **Sound:** play a short notification sound on new messages.
5. **Focus-aware:**
   - Terminal **not focused**: pop-up + sound, for any chat, including the open one.
   - Terminal **focused**: sound only, for any chat. No pop-up.
6. **Mute, one shared state with WhatsApp:**
   - Mutes made on the phone (or any linked device) are respected, including timed mutes that expire.
   - `/mute [duration]` and `/unmute` in whatscli mute the chat **on WhatsApp**, so the phone and other devices follow too.
   - Muted chats make no pop-up and no sound. Unread counts still go up as now.

## Non-goals

- Clicking a notification to open the chat.
- Per-chat custom sounds, notification history, Do Not Disturb schedules.
- Notifications for reactions, edits, revokes, receipts or presence.
- A whatscli-only mute that differs from WhatsApp's (decided against: see Approaches).

## Anti-goals (would make this a failure even if it works)

- Shipping WhatsApp's own notification sound or any asset we don't have rights to.
- Linking an audio library or any new C dependency (the build already needs CGO for SQLite; audio would add ALSA/CoreAudio headers): it would grow the binary and complicate release builds.
- A burst of notifications at startup or during history sync.
- Notifications that block or slow the UI. Playing sound and showing the pop-up run in the background.
- Regressing current behaviour in terminals that don't report focus.

## Approaches considered

**Mute**
- **A. Mute on WhatsApp itself (chosen).** `/mute` sends an app-state patch (`appstate.BuildMute` / `BuildMuteAbs` in whatsmeow, sent with the client's `SendAppState`). Phone mutes arrive as `*events.Mute` and, at startup, as `Conversation.MuteEndTime` in history sync. One state, stored locally. Chosen because there is no "why is this chat silent?" confusion, and muting once mutes everywhere.
- B. A separate whatscli-only mute alongside phone mutes. Rejected: two states that can disagree.

**Sound source**
- **A. Our own generated sound (chosen).** A short two-note pluck, similar in spirit to WhatsApp's tone but not a copy, generated by a small Go program in the repo. We own it outright, and it's only a few KB.
- B. A CC0 sound from Freesound. Rejected: digging through sounds and checking each licence, for a match we can approximate ourselves.

**Sound playback** (decided earlier with the user)
- Run the system player instead of linking audio code. See Design.

## Design

### The decision (pure function, unit-tested)

```
decide(msg, chat, now, focus, lastNotified) -> (popup bool, sound bool)
```

In order:
1. `enable_notifications` false → nothing.
2. From me → nothing.
3. Older than 30 s (keeps the existing rule; stops history-sync bursts) → nothing.
4. Chat muted at `now` → nothing.
5. Chat notified within `notification_timeout` s → nothing. Otherwise record `now` for the chat.
6. Focus:
   - `unfocused` → popup + sound.
   - `focused` → sound only.
   - `unknown` (terminal has not reported focus since start): keep today's behaviour exactly. Open chat → nothing; other chats → popup + sound. *(Design call: no regression in terminals without focus reporting, such as tmux without `focus-events on`.)*

Throttle state is in memory only; it resets on restart.

### Pop-up

- `beeep.Notify(title, body, "")` as today, run in a goroutine; errors go to `PrintError` as now.
- Title: the sender label from `senderLabel` (as now); for groups, `"<sender> · <group name>"` with the group name from `getChatName` (already resolved in `processIncomingMessage` as `chatName`).
- Body: `text`, else `preview`, else `"New message"`. Single line, cut to about 100 runes with `…`.

### Sound

- Settings in `[general]`:
  - `notification_sound` (default empty = built-in sound; otherwise a path to the user's own file, `~` expanded).
  - `play_sound` (default `true`).
  - `use_terminal_bell` (existing): when true, the bell replaces the sound. The pop-up still shows. `play_sound = false` silences both the sound and the bell. *(Design call.)*
- Built-in sound: a WAV (16-bit PCM, mono, 44.1 kHz, under 0.4 s), embedded with `go:embed`. It is written once to the user cache dir (`os.UserCacheDir()/whatscli/notify.wav`) when first needed, because players need a file path.
- The generator lives at `tools/gen-notify-sound/main.go` (standard library only). It writes the WAV into the package that embeds it. The repo commits both the generator and its output. The sound: two quick ascending notes with a fast attack and a short exponential decay, plus a soft harmonic for a "pluck" feel. Keep the volume moderate (peak about -6 dBFS).
- Player, found once with `exec.LookPath` and cached:
  - Linux and BSD: `pw-play`, then `paplay`, then `aplay -q`.
  - macOS: `afplay`.
  - Windows: `powershell -NoProfile -Command "(New-Object Media.SoundPlayer '<path>').PlaySync()"`.
  - None found → terminal bell.
- Run with `exec.CommandContext` and a 5 s timeout, in a goroutine. Wait on the process so no zombies are left. At most one sound plays at a time; a new one while one is playing is skipped.
- The terminal bell has to go through the UI: today's `fmt.Printf("\a")` writes behind tview's back. Use tcell's `Screen.Beep()` via the app's screen. (The builder should confirm this works with the current setup.)

### Focus tracking

- tcell v2.13 supports focus reporting (`Screen.EnableFocus()`, `*tcell.EventFocus{Focused bool}`). But tview v0.42's event loop (`application.go` ~l.400) only handles key, paste, resize, mouse and error events, so it drops focus events.
- Plan: create the tcell screen ourselves, call `EnableFocus()`, and hand tview a thin wrapper `Screen` (embedding `tcell.Screen`). The wrapper intercepts event delivery, records focus in an atomic value (`unknown`, `focused` or `unfocused`), and passes every other event through unchanged. Install it with `App.SetScreen`. tview v0.42 reads events with `screen.PollEvent()` (`application.go:343`), so the wrapper overrides `PollEvent`. Focus state reaches the `messages` package through the existing UI handler interface or a small exported setter; builder's choice.
- tmux users need `set -g focus-events on`. Document it.

### Mute

- Source of truth: **whatsmeow's own chat settings store** (`Store.ChatSettings`, in `session.db`). whatsmeow writes every mute it receives there (`PutMutedUntil`, `appstate.go` ~l.266), including on the full app-state sync after login, even though it does not emit `*events.Mute` for full syncs (`EmitAppStateEventsOnFullSync` stays false). So mutes made on the phone before this version are already there for paired users. Read with `GetChatSettings(ctx, jid).MutedUntil`; `store.MutedForever` means forever, zero time means not muted. *(Design call, replacing an earlier plan for a new `conversations.mute_end_time` column: that column would have missed existing mutes for already-paired users. No schema change.)*
- In memory: a small cache `map[chatJID]time.Time` in the session manager, filled lazily from the store and updated on `*events.Mute` and after `/mute` / `/unmute`. It is used by `decide()` and the chat-list marker, so drawing the list does not hit SQLite per row. Use `canonicalChatJID` for keys, and check both the LID and phone-number JIDs of a chat when looking up (a mute may be stored under either).
- `muted(now) = until == MutedForever || until.After(now)`.
- Live changes: add a `*events.Mute` case to the event switch in `event_handler.go`. Update the cache from the event (`Action.GetMuted()`, `GetMuteEndTimestamp()` in ms, negative = forever) and redraw the chat list.
- Commands:
  - `/mute` mutes the open chat forever; `/mute 8h`, `/mute 1w` and `/mute 30m` set a duration (Go durations, plus `d` and `w`). `/unmute` unmutes. Both act on the open chat.
  - They send `appstate.BuildMute(jid, mute, duration)` via `client.SendAppState`. Update the cache **only on success** (whatsmeow updates its store when the patch comes back); on failure, print the error. If offline, say so and change nothing.
  - Add them to the command list, `/help`, the help window and the README.
- Chat list: show a muted marker (the speaker-off symbol, U+1F507) next to the time for muted chats. *(Builder's call: you can't tell a chat is muted without it.)*

### Settings summary (`[general]`)

**Table N1: notification settings**

| Key | Default | Notes |

| `notification_timeout` | `60` | now implemented, per chat |

## Testing

- `decide()`: a table test covering every rule and the focus states, including expiry of a timed mute and the throttle window.
- Title and body formatting: direct chat, group, media-only, long text, multi-line text.
- Mute: event handling (timed, forever, unmute), cache filled from a fake `ChatSettings` store, lookup across LID and phone-number JIDs, expiry.
- `/mute` duration parsing (`8h`, `1d`, `1w`, bad input).
- Player selection with a fake `LookPath`.
- The focus wrapper passes non-focus events through untouched and updates state on `EventFocus`.
- Manual check: a live run in a focus-reporting terminal (and in tmux with `focus-events on`), covering pop-up and sound with the terminal unfocused, sound only with it focused, a phone mute respected, and `/mute 1h` showing on the phone.
