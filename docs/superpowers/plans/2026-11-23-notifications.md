# Notifications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

_Last updated: 2026-11-23T08:57:07+00:00 (first draft)_

**Goal:** Notifications that can stay on all day: group-aware titles, readable bodies, a per-chat throttle, a built-in sound, focus-aware pop-ups, and mutes shared with WhatsApp (`/mute`, `/unmute`).

**Architecture:** A pure decision function (`notifier.decide`) in `messages/notify.go` chooses pop-up and/or sound from the message, mute state, open chat, terminal focus, and throttle. Mute state is read from whatsmeow's `Store.ChatSettings` through an in-memory cache. Sound is an embedded WAV played by the system player. Terminal focus comes from a `tcell.Screen` wrapper in package `main` that reports `EventFocus` to the session manager, because tview v0.42 drops focus events.

**Tech Stack:** Go (CGO on, as today), whatsmeow `v0.0.0-20261030132714-6f46ecaf9e95`, tview v0.42.0, tcell v2.13.10, beeep (existing), `gopkg.in/ini.v1` (existing).

**Spec:** `docs/superpowers/specs/2026-11-23-notifications-design.md`

## Global Constraints

- Every Go file starts with `// SPDX-License-Identifier: AGPL-3.0-only` (CI: `.github/scripts/check-spdx.sh`).
- No new module dependencies. The sound generator uses the standard library only.
- No audio library and no new C dependency. Play sound by running `pw-play`, `paplay`, `aplay -q` (Linux and BSD), `afplay` (macOS), or PowerShell `Media.SoundPlayer` (Windows).
- Never read `sm.client` directly; use `sm.getClient()`. Never hold `sm.mu` during DB writes, network calls, or `client.Store` lookups. Never block `runManager` or the tview event loop.
- Chats may be `@lid` or `@s.whatsapp.net`: use `canonicalChatJID` / `sameUser` (`messages/jid_norm.go`).
- Notifications and sounds run in goroutines; a failure is reported with `sm.uiHandler.PrintError` and never blocks message handling.
- Do not ship any WhatsApp or Meta asset. The sound is generated by `tools/gen-notify-sound`.
- Config defaults (`[general]`): `enable_notifications = true`, `use_terminal_bell = false`, `notification_timeout = 60`, `play_sound = true`, `notification_sound = ""`.
- Docs: UTC timestamp from `date -u --iso-8601=seconds` on every doc you touch, label every table, no emojis or em-dashes in docs, and keep README, CHANGELOG, ROADMAP and ARCHITECTURE current in the same change.
- Before calling a task done: `gofmt -l .` prints nothing, `go build ./...`, `go vet ./...`, and `go test -race -count=1 ./...` all pass.
- Do not run against a real WhatsApp account and do not touch `~/.config/whatscli`. The live check in Task 8 is for the user.
- Commits stay local on `feature/notifications`. Never push.

## Review Focus

1. **Reconnect burst:** after a short drop, many messages under 30 s old arrive at once from several chats. Expect at most one notification per chat (Task 1 test `TestDecideBurstAcrossChats`).
2. **Timed mute expiry:** a chat muted for 1 h on the phone notifies again after the hour without a restart, because the cache stores the end time, not a bool (Task 4 test `TestMuteExpiresWithoutRestart`).
3. **Markup in message text:** on Linux, notification daemons render body markup, so a message `<b>hi</b> & co` must show those characters literally (Task 2 test `TestNotifyBodyEscapesMarkupOnLinux`).
4. **Bad `notification_sound` path:** a missing or unreadable file gives one clear error, then falls back to the built-in sound (Task 3 test `TestSoundFileFallsBackOnBadPath`).
5. **Broken audio setup:** a player that exits with an error (for example no audio server) is reported once per session, not on every message (Task 3 test `TestPlayerErrorReportedOnce`).

### Task 3: Built-in sound and the player

**Files:**
- Create: `tools/gen-notify-sound/main.go`, `messages/sound/notify.wav` (generated), `messages/sound.go`
- Test: `messages/sound_test.go`

**Interfaces:**
- Produces:
  - `//go:embed sound/notify.wav` → `var builtinSound []byte`
  - `func soundFile(custom string, cacheDir string) (path string, warn error)`. With an empty `custom`, it writes `builtinSound` to `<cacheDir>/whatscli/notify.wav` if missing or different, and returns that path. With a `custom` that exists and is a regular file, it returns the `~`-expanded `custom`. Otherwise it returns the built-in path and a non-nil `warn` naming the bad path.
  - `func pickPlayer(goos string, lookPath func(string) (string, error), file string) (cmd string, args []string, ok bool)`
  - `type soundPlayer struct` with `func newSoundPlayer(report func(error)) *soundPlayer` and `func (p *soundPlayer) Play(file string)`. `Play` is non-blocking; at most one sound plays at a time, and a call during playback is dropped. It waits on the process under a 5 s `exec.CommandContext` timeout. The first error from the player goes to `report`; later errors are silent. A `run func(ctx, name string, args ...string) error` field (default runs `exec.CommandContext(...).Run()`) lets tests replace it.

- [ ] **Step 1: Write the generator** `tools/gen-notify-sound/main.go` (package main, standard library only). It writes `messages/sound/notify.wav`: 16-bit PCM, mono, 44100 Hz, total length under 0.4 s (aim for about 0.25 s). Use two ascending notes (about 880 Hz, then about 1320 Hz, each about 90 ms with a 10 ms gap). Each note has an attack under 5 ms, an exponential decay, and a second harmonic at about 0.3 amplitude. Normalise the peak to -6 dBFS (16422). Add a `//go:generate go run ../tools/gen-notify-sound` line in `messages/sound.go`, then run `go generate ./messages`. Listen to it with `pw-play messages/sound/notify.wav` and adjust until it sounds like a short, friendly pluck.
